# Дополнение к требованиям: справочник, журнал и напоминания

Дата: 06.11.2026. Уточняет ФТ-02, ФТ-09, ФТ-12, ФТ-13 и ФТ-16.
Нормативные схемы и сценарии включены в OpenAPI и CSV каталога проверок.

## Справочник сотрудников

- `GET /users/directory`: ADMIN и ENGINEER, только чтение; `role`, `status`,
  `q`, `limit`, `offset`, порядок `login ASC,id ASC`.
- `GET /users/{user_id}/summary`: краткий профиль `id/login/role/status`.
  ADMIN и ENGINEER читают любой профиль. TECHNICIAN и OPERATOR читают себя и
  участников доступных им заявок/событий. Техник также видит автора связанной
  неисправности. При отсутствии связанного доступа возвращается 404.
- После переназначения прежний техник теряет связанный доступ, если нет других
  доступных работ с тем же участником. Статус BLOCKED участника не скрывает его
  имя в истории.
- Административные `GET/POST /users` и `GET/PATCH /users/{user_id}` остаются
  исключительно за ADMIN. Пароли, хеши, версии и временные метки профиля
  не включаются в справочник.
- Для назначения выбираются только ACTIVE TECHNICIAN. Фильтры заявок и истории
  используют весь справочник, включая заблокированных и сменивших роль сотрудников.
  Клиент читает все страницы, а не только первые 100 записей.

## Журнал заявки

Новые служебные `details` записываются на русском. Результат выполнения,
причина отмены и комментарий к операции сохраняют текст пользователя.
Клиент отображает эти сведения как текст; HTML не исполняется.
Лимит `details` составляет 4000 символов и соответствует допустимой длине
результата выполнения: пользовательский текст не обрезается.
Старые события не переписываются: известные английские служебные строки
отображаются через русский тип события. Произвольный пользовательский текст,
включая английский, остаётся видимым.

## Напоминания

Создание/изменение регламента, изменение состава или активности графиков,
назначение/переназначение техника и закрытие плановой работы формируют актуальные
уведомления в той же транзакции. Ошибка формирования откатывает изменение целиком.
Проверяются только затронутые графики; обработчик ARQ использует ту же генерацию.
Worker запускается каждую минуту для смены даты и изменений состава получателей.

Окна T−3..T−1 и T/просрочка, прекращение после COMPLETED и ключ уникальности
`schedule_id + planned_due_on + type + recipient_id` сохраняются.
Если первый срок дальше трёх дней, немедленного напоминания нет.
Старые уведомления сохраняются. После локальных команд клиент обновляет кэш;
для изменений от других пользователей опрашивает уведомления раз в 30 секунд.

## Проверка

Проверяются запреты административных операций для инженера, фильтры справочника,
пагинация, потеря связанного доступа, видимость авторов/исполнителей, безопасный
вывод `details`, уведомления до worker tick и отсутствие дублей после повторного tick.
