# Mini-CMMS API 1.0.0: примеры и инструкция приёмки

Это план проверок будущей реализации. Статическая валидация не означает, что API/БД/worker существуют
или что бизнес-сценарии выполнены на сервере. Примеры синтетические, рабочие credentials здесь не хранятся.

## 1. Статические проверки

Из корня проекта:

```bash
uv run --no-project --with pyyaml --with 'jsonschema[format]' --with openapi-spec-validator \
  python backend/Mini_CMMS_API_Validation.py
```

Зависимости относятся к проверке контракта, а не к реализованному приложению. `jsonschema[format]`
обязателен: без extras обычная установка может молча не проверять `date-time`/URI. Скрипт проверяет
доступность checker и содержит отрицательные пробы, которые должны отклоняться.

Проверяются структура OAS 3.1.1, схемы Draft 2020-12, ссылки, повторные YAML-ключи, operationId,
параметры пути, форматы, положительные и ошибочные примеры, заголовки, бизнес-инварианты response-схем,
успешный сценарий каждой операции, объявленные статусы/коды ошибок, идентичность всех полей YAML/CSV,
схемы запросов/ответов сквозных примеров и арифметические границы раннего ТО.

Число примеров не является мерой полного покрытия. Каталог CSV описывает проверки, а не реализует HTTP runner.
Реальные ограничения FK/UNIQUE, блокировки, права, токены, часы, ARQ и побочные эффекты проверяются ниже.
Flow checker сверяет эффективный BearerAuth, соответствие placeholder сессии actor и различает отзыв
от истечения: для REVOKED отказ 401 должен происходить до expires_at. В протокольных кейсах структурно
заданы Allow и отсутствие изменений, а транспортный код ограничен CONNECTION_FAILED.

## 2. Общая фикстура и правила исполнения

1. Для каждого flow из [Mini_CMMS_API_Examples.yaml](Mini_CMMS_API_Examples.yaml) — новая тестовая БД либо
   изолированный rollback и заново созданный initial_state. Каждая запись initial_state передаётся через
   тестовую фабрику; это не публичный API и не инструкция записи в production.
2. В фикстуре есть ACTIVE ADMIN, ENGINEER, TECHNICIAN, OPERATOR. Для отрицательных проверок добавить
   второго техника/оператора, чужие объекты и BLOCKED пользователя. Пароль `SyntheticPass-2026!` —
   публичное синтетическое значение; фабрика хранит его хеш. Реальные секреты сюда не подставлять.
3. `company_timezone=Europe/Moscow`. Часы приложения/worker внедряются тестовой зависимостью;
   `clock_utc` явно задаёт момент каждого шага. Публичного endpoint изменения часов нет.
4. `actor` задаёт пользователя; bearer получают через login в setup либо показанным шагом. В flow с
   переходом на другую дату вход повторяется: сессия действует 12 ч. Образец token в expected_body
   не сравнивают буквально: проверяют формат, expires_at=issued_at+12ч и работоспособность отзыва.
5. UUID/number новых объектов, токены, IDs event/history связывают с фактическим ответом. Их подставляют
   во все последующие запросы и expected_body; существующие fixture UUID фиксированы. Для unit/integration
   среды допустим контролируемый генератор UUID. Остальные значения сравнивают с примерами.
6. Path запроса = `/api/v1` + path_template с подстановкой path_params. Query кодируют отдельно, JSON body
   сериализуют как JSON; заголовки не переносят в тело. If-Match включает кавычки и относится к нужному
   ресурсу. Для checklist — к WorkOrder. Пример заголовка: `If-Match: "<work_order_id>:3"`.
7. Успех создания: проверить HTTP, Content-Type, полное тело по схеме, Location с тем же id, затем GET.
   Изменение: проверить версию/ETag, данные и связанные эффекты. Ошибка: HTTP, ProblemDetail.status/code,
   отсутствие утечки чужого объекта и **отсутствие изменений**, в том числе event/history/version.
8. Каждый flow исполняется последовательно; standalone examples внутри OpenAPI — независимые состояния,
   их нельзя без подготовки считать одним общим состоянием БД. Не сравнивают `detail` буквально;
   стабильны status/code и заявленные инварианты. Заголовки HTTP сравнивают без учёта регистра имён.

## 3. Четыре сквозных сценария

Полные request/expected_body/headers и моменты времени находятся в YAML примеров.

**repair:** вход оператора/инженера/техника → оборудование → неисправность → REPAIR → assign → start →
complete → close → Fault → WorkHistory. Ожидаются Fault OPEN→IN_PROGRESS→RESOLVED, одна история,
пять событий, прежний ручной статус оборудования. Повторный close: 409 и ровно прежняя история.

**planned:** CATEGORY-план на компрессоры → индивидуальный график → PLANNED заранее → assign → start →
два PATCH обязательных пунктов → complete → close на следующий день → график. После первого PATCH
добавлена попытка со старым ETag: 412 и никакого эффекта. COMPLETE 05.11.2026 20:30Z соответствует
05.11 в Moscow; close 06.11 не переносит расчёт: last_completed_on=05.11, next_due_on=05.12 при 30 днях.
На заявку семь событий; отклонённый PATCH событие не создаёт.

**cancel_and_recreate:** REPAIR по OPEN Fault → cancel CREATED с причиной → повтор cancel 409 → новый
REPAIR по тому же Fault. Старый наряд CANCELLED, новый CREATED; Fault OPEN, истории нет.
Отдельно повторить этот путь для ASSIGNED и PLANNED того же schedule+due.

**block_and_revoke:** login OPERATOR → ADMIN блокирует его с текущим If-Match → старый bearer даёт 401 →
ADMIN разблокирует → тот же старый bearer по-прежнему 401. Новый login успешен; записи пользователя
и производственные ссылки сохранены. Повторить для смены пароля, logout и истечения 12 часов.

## 4. Раскрытие каталога тестов

Каждая строка CSV имеет ID, фактический метод/путь, operationId, предусловие, ожидаемый HTTP/code и эффект.
Те же поля обязаны совпадать с `x-corner-cases`. Базовая фикстура P01 — положительный пример операции;
операции, не участвующие в четырёх flow, тестируют на отдельном подготовленном состоянии из их examples.
Для POST/PATCH брать body из request examples, а состояние готовить под operation description. Не считать
успешный HTTP достаточным: проверяются все постусловия и повторное чтение.

Для каждой операции раскрыть следующие измерения в отдельные проверки, параметризацией по JSON Schema:

- Без bearer; случайный/просроченный/отозванный токен; BLOCKED; каждая из четырёх текущих ролей.
  Публичные операции не требуют токена. У авторизованной запрещённой роли 403; у допустимой роли на
  чужой объект 404. Для OPERATOR отдельно REPAIR допустим, PLANNED запрещён.
- Невалидный UUID и валидный отсутствующий UUID; видимый и скрытый объект; скрытые UUID в теле и фильтрах;
  item_id чужой заявки. GET/списки/history/events/notifications не раскрывают чужие данные и total.
- Каждое required: отсутствует/null/неверный тип; неизвестное поле; каждая граница min/max и соседнее
  недопустимое значение; неизвестный enum; пустые/пробельные строки; формат date/date-time/UUID.
  bool не подменяет integer. Пустой PATCH 422; поддерживаемый null comment допустим, прочий null — 422.
- Повреждённый JSON, неподдерживаемый Content-Type, 201 Location, 204 без тела, 401 challenge,
  429 Retry-After, 405 Allow. Протокольные случаи из `x-protocol-test-cases` проверяют фактический
  неподдерживаемый метод; транспортный отказ имеет пустой HTTP, не статус 0.
- PATCH: текущий ETag — успех; отсутствует — 428; неверный синтаксис/wildcard/weak/list — 422; чужой или
  старый — 412; no-op — 200 с прежней версией. Автоматическое изменение Fault и изменение checklist
  инвалидируют предыдущий ETag соответствующего ресурса.
- Каждая команда WorkOrder из каждого статуса. Успехи ровно по таблице notes; остальные состояния — 409.
  Чужой техник не может start/complete/checklist; ENGINEER не подменяет техника. CLOSED/CANCELLED immutable.
- Поиск: регистр, кириллица, буквальные `%`/`_`, отсутствие результата, несколько полей OR внутри q и
  AND с остальными фильтрами. Права применяются к результату до total/пагинации.
- Пагинация: limit=1/100/0/101, offset=0/total/больше total/−1, пустой набор; равные ключи сортировки,
  все режимы sort; обратный диапазон дат. При неизменном наборе нет пропусков/дублей между страницами.
- Архив/restore/смена категории/пауза/возобновление плана; старый schedule.id и даты сохраняются.
  Подключение нового станка при прошлом first_due_on даёт local_today; до первого ТО изменение интервала
  дату не меняет. После первого ТО — формула от last_completed_on, включая просрочку.

Фиксировать каждый раскрытый тест как `<case-id>[<role/field/boundary>]` в отчёте runner. Каталог не
обещает перебор всех возможных строк/дат; он задаёт проверяемые классы эквивалентности и инварианты.

## 5. Время и напоминания: точные ожидания

Фикстура: два станка одного CATEGORY-плана с независимыми schedule, T=05.11.2026; два ACTIVE ENGINEER;
один ACTIVE TECHNICIAN назначен первому станку, второму никто не назначен. Worker вызывается явно через
тестовую функцию, не HTTP endpoint. Время tick и company_timezone фиксируются.

| Момент | Новые записи после первого tick | После повторного/параллельного tick |
|---|---|---|
| T−4 | 0 | 0 |
| T−3 | 5 THREE_DAYS_BEFORE | 0 новых |
| T−1, до этого запусков не было | 5 THREE_DAYS_BEFORE | 0 новых |
| T, пропущено всё предварительное окно | 5 ON_DUE_DATE, 0 предварительных | 0 новых |
| T+2, до этого запусков не было | 5 ON_DUE_DATE | 0 новых |
| Текущий наряд первого станка COMPLETED | Для него 0, для второго 2 по актуальному типу | 0 новых |

Каждая строка — отдельный reset, если не указано продолжение. При двух типах, созданных в разные окна,
раньше созданные записи сохраняются: всего может быть десять, но повторный tick ни одну не дублирует.
После позднего назначения второго станка технику в T−1 — одна новая предварительная запись, затем ноль.
После reassign в актуальном окне — одна запись новому ACTIVE TECHNICIAN; старое уведомление сохраняется.
BLOCKED получатель, выключенный план, архивный/неподходящий станок: новых записей нет.

Временные границы: T−3 00:00, T 00:00 и соседние секунды по company_timezone; 29.02 високосного года,
конец месяца/года. Проверить момент `2026-10-06T21:30:00Z`: в Moscow уже 07.10, поэтому ТО со сроком
05.11 и интервалом 30 дней допустимо. В `20:59:59Z` ещё 06.10 — TOO_EARLY_TO_COMPLETE.
При интервале 1 день завершение за день до срока запрещено; в день срока допустимо.

Изменение интервала: CLOSED срок 05.11, фактическая дата 20.10. Новый интервал 16 запрещён (05.11 не позже
закрытого срока), 17 разрешён (06.11). Для CATEGORY-плана с одним конфликтующим графиком весь PATCH
откатывается, включая остальные графики и version плана. Даты не изменяются скрыто при archive/restore.

## 6. Конкуренция и атомарность

Использовать независимые соединения/транзакции и управляемый barrier перед проверяемой записью.
Последовательные повторы не заменяют конкурентный тест. После обеих транзакций читать состояние из
третьего соединения. Проверять обе HTTP-ветки, количество строк, FK, version и event/history.

| Гонка | Допустимые исходы и инвариант |
|---|---|
| Два создания по одному Fault/графику | 201 + 409; один незавершённый наряд и одно событие CREATED |
| Два assign/start/complete/close/cancel | 200 + 409; один переход/эффект, history единственная |
| cancel ASSIGNED против start | 200 + 409; либо CANCELLED и Fault OPEN, либо IN_PROGRESS и Fault IN_PROGRESS |
| Два PATCH одной версии | 200 + 412; одно изменение, version+1, событие только победителя |
| archive против createWorkOrder | create 201 + archive 409 либо archive 200 + create 409; активной работы на архиве нет |
| Два tick ARQ | Итог ровно по получательскому UNIQUE, без дублей |
| Два последних ADMIN понижают/блокируют друг друга | Никогда ноль ACTIVE ADMIN; при barrier после auth один 200, второй 409; при поздней auth допустим отказ 401/403 |
| close против смены interval/категории | Общий порядок блокировок; либо изменение отклонено из-за незавершённой работы, либо пересчёт согласован с одним CLOSED; без потерянной даты |

Инъекция ошибки перед commit в close/создание/пересчёт/отмену: после отката неизменны WorkOrder, Fault,
график, история, event и version. Отдельно проверить межпроцессную уникальность login/inventory_number.
При всех отказах не должно оставаться частично созданных schedules или snapshot чек-листа.

## 7. Трассировка требований и отдельные runtime-гейты

| Требования | Минимальное доказательство |
|---|---|
| ФТ-01–03 | Вход, матрица всех ролей, блокировка/смена пароля/роли, токен после отзыва, последний ADMIN |
| ФТ-04–06 | CRUD допустимых полей, поиск/фильтры, Fault, архив/restore, права и даты |
| ФТ-07–09 | Графики CATEGORY/EQUIPMENT, snapshot, временная матрица и управляемые worker tick |
| ФТ-10–15 | repair/planned/cancel flows, все команды/состояния, FK, immutable history/events |
| ФТ-16–17 | Поиск/сортировка/пагинация/диапазоны, schema boundaries, ошибки и If-Match |
| ФТ-18, НФТ-05 | Повторное чтение, перезапуск с сохранённым volume, транзакции, ограничения и история |
| НФТ-01 | Запуск/демонстрация, раздельные health/ready; это не гарантия 24/7 |
| НФТ-02 | До 300 станков/1000 заявок; минимум 5 повторов основных операций, каждое измерение и среда записаны; целевое время до 3 с |
| НФТ-03–04 | Специализированные хеши, серверные права, TLS для внешней среды, отсутствие секретов в коде/логах; проверка конфигурации |
| НФТ-06–07 | Формы/ошибки и реальные версии Chrome/Firefox/Edge/Safari; отсутствующие среды явно отмечены |
| НФТ-08 | Нет функций за согласованными границами MVP |
| НФТ-09 | Backup PostgreSQL → новая тестовая БД → сверка контрольных пользователей, Fault, orders, schedules, history; рестарт не заменяет restore |
| НФТ-10 | Контролируемая ошибка API/worker видна в журнале с временем/типом; без пароля/токена/DSN |
| НФТ-11 | Перед реальным внедрением согласованы данные/хранение/доступ; API не является доказательством правового соответствия |

Протокол результата: версия/SHA256 контракта и SHA реализации, команды, версия БД/Redis/worker,
timezone и часы, fixture, ID раскрытых тестов, оба ответа гонок, результаты SQL/GET, ссылки на логи без
секретов. Статические проверки, integration, UI, производительность, backup, deploy и бизнес-сценарии
отмечаются раздельно. Ни один невыполненный гейт не помечается PASS на основании другого.
