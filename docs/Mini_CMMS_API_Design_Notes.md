## 1. Границы MVP

Вход, сотрудники и серверные роли, оборудование, неисправности, регламенты и индивидуальные графики ТО,
внутрисистемные напоминания, ремонтные и плановые заявки, назначение, выполнение, приёмка, отмена до начала,
snapshot чек-листа, журнал событий, неизменяемая история закрытых работ, поиск и фильтры.

Вне MVP: публичная регистрация, refresh, восстановление пароля по почте, SSO, файлы/фото, QR, календарный UI,
IoT, склад, закупки, финансы, email/Telegram, аналитика. Backup/restore — административная процедура и отдельная
проверка НФТ-09, не HTTP endpoint. Начальная учётная запись ADMIN создаётся процедурой развёртывания.
При подключении оборудования прошлые работы не выдумываются: `last_completed_on=null`, первый срок задаётся
регламентом с правилом подключения ниже. Импорт исторических работ не входит в MVP.

## 2. Протокол и валидация

- Base path `/api/v1`, UUID, JSON. Создание: 201 с объектом и `Location=/api/v1/<collection>/<id>`.
  Logout: 204 и пустое тело. GET ничего не изменяет, в том числе не отмечает уведомление прочитанным.
- Даты: `YYYY-MM-DD`; временные метки: RFC3339 UTC с `Z`. Календарные вычисления: `company_timezone`,
  IANA-настройка сервера; примеры используют `Europe/Moscow`. Смена timezone действующего предприятия
  требует отдельной миграционной политики и не является операцией этого API.
- Неверный синтаксис JSON: 400 `MALFORMED_JSON`; неподдерживаемый Content-Type: 415 `UNSUPPORTED_MEDIA_TYPE`.
  Структурно неверное тело, неизвестные поля, некорректные UUID/enum/даты/параметры: 422 `VALIDATION_ERROR`.
  Обратный диапазон дат: 422 `INVALID_DATE_RANGE`. `application/json; charset=utf-8` допустим.
- В обязательных текстовых полях недопустимы одни пробелы. Сначала проверяются ограничения JSON Schema
  сырого входа, затем внешние пробелы деловых строк обрезаются, повторно проверяется длина и проверяется
  уникальность перед сохранением; пароль не меняется и не обрезается. Login соответствует ASCII
  pattern схемы; сравнивается без учёта регистра. Инвентарный номер и категория после обрезки сравниваются
  точно, с учётом регистра. Чек-лист: уникальные `order` и названия после нормализации последовательностей
  пробелов до одного; регистр названий значим. Порядок элементов ответа: `order ASC,id ASC`.
- Дата ввода и дата обнаружения не могут быть позже local_today. `first_due_on` может быть прошлой датой;
  график подключения использует max. Дополнительная граница detected_on относительно commissioned_on
  исходными требованиями не задана и этим контрактом не вводится.
- PATCH: пропуск поля = без изменения; null допустим только по схеме; пустой объект запрещён.
  Изменение переданных значений атомарно. Неизменившийся PATCH возвращает 200 без новой версии/события.
- Ошибки: `application/problem+json`, профиль RFC 9457; `type` и, если присутствует, `instance` — URI reference,
  `instance` не null. HTTP совпадает с `status`; `code` стабилен, текст `detail` не является машинным кодом.
  Примерный домен `mini-cmms.example` — идентификатор типа, не требование внешнего сетевого запроса.
- 401: нет действующей сессии; `WWW-Authenticate: Bearer`. Вход с неизвестным login/неверным паролем/BLOCKED
  всегда даёт одинаковый 401 `INVALID_CREDENTIALS`. 403: текущая роль не разрешает операцию/тип создаваемого
  наряда. 404: объект отсутствует либо скрыт от допустимой роли; та же проверка применяется к связанным UUID.
  409: конфликт состояния/уникальности, 412: версия изменилась, 428: отсутствует If-Match, 429: лимит входа.
- Приоритет: аутентификация → роль → видимость конкретного доступного для разбора UUID → валидация
  тела/параметров/If-Match → precondition → бизнес-правила → атомарная запись. Невалидный UUID при действующей
  допустимой роли даёт 422. Неавторизованный запрос не используется для выяснения состояния чужого объекта.
- `GET /health`: 200 `status=ok`, если HTTP endpoint отвечает; БД/Redis не проверяются. Остановленный процесс —
  транспортная ошибка без HTTP-статуса. `GET /ready`: PostgreSQL и Redis доступны — 200, иначе 503.
  Readiness не доказывает исправность worker или выполнение бизнес-сценария.
- Неподдерживаемый метод существующего пути: 405 `METHOD_NOT_ALLOWED`, ProblemDetail и `Allow` с разрешёнными
  методами. Эти тесты находятся в `x-protocol-test-cases`, а не изображают GET, вернувший 405.

## 3. Сессии и роли

Одна роль на пользователя: ADMIN, ENGINEER, TECHNICIAN, OPERATOR; ACTIVE/BLOCKED.
Opaque bearer, хеш токена в БД, срок 12 часов от выдачи, без продления по активности.
Logout отзывает текущий токен. BLOCKED и смена пароля отзывают все токены; разблокировка их не оживляет.
Каждый защищённый запрос проверяет текущую роль и состояние. Логи не содержат пароли и токены.

После пяти INVALID_CREDENTIALS в скользящем окне 10 минут по IP **или** lowercase(login) следующая попытка
даёт 429; `Retry-After` — секунды до освобождения окна. Успешный вход окно не обнуляет; 400/422 не считаются
неудачной проверкой пароля. Лимит должен действовать атомарно при нескольких запросах/процессах API.

| Область | ADMIN | ENGINEER | TECHNICIAN | OPERATOR |
|---|---|---|---|---|
| Пользователи | Все операции | Нет | Нет | Нет |
| Оборудование | Нет | Всё | Связанное с текущими назначениями | Неархивное |
| Неисправности | Нет | Все | Связанные с текущими назначениями | Свои; создать/исправить по правилам |
| Регламенты/графики | Нет | Всё | Связанные с текущими назначениями | Нет |
| Заявки | Нет | Все; создать/изменить/назначить/принять/отменить | Свои назначения; начать/чек-лист/выполнить | Свои; создать только REPAIR |
| История | Нет | Вся | Завершённые им работы | По собственным заявкам |
| Уведомления | Нет | Только свои | Только свои | Нет |

Списки и total фильтруются **до** пагинации. После reassign прежний техник теряет незавершённую заявку и
связанный через неё доступ. CLOSED/CANCELLED сохраняют assignee_id; текущее назначение на такую запись
можно читать, изменять её нельзя. Смена роли оставляет данные, но применяет права новой роли.
Машинная матрица каждой операции: `x-allowed-roles`, `x-object-visibility`; определения — `x-visibility-rules`.
Ссылки из тела, фильтры и journal/history не обходят объектные ограничения.

Последнего ACTIVE ADMIN нельзя понизить/заблокировать, в том числе конкурентно.
Смена роли TECHNICIAN запрещена при его незавершённых назначениях до перераспределения/приёмки/отмены.
Блокировка техника допустима: ENGINEER переназначает ASSIGNED/IN_PROGRESS, либо закрывает его COMPLETED.

## 4. Версии и конкурентное изменение

User, Equipment, Fault, MaintenancePlan, WorkOrder имеют `version>=1`.
GET конкретного ресурса и ответ изменения возвращают сильный `ETag: "<uuid>:<version>"`.
Каждое фактическое изменение, в том числе автоматическое изменение Fault и действие над WorkOrder,
атомарно увеличивает version. Списки содержат version в элементах; ETag списка не используется для PATCH.

Каждый PATCH требует **один** сильный If-Match из последнего GET: нет — 428 PRECONDITION_REQUIRED;
невалидный, weak, wildcard или список — 422; синтаксически допустимый устаревший/чужой — 412 VERSION_CONFLICT.
Версия проверяется под блокировкой либо условным UPDATE вместе с записью. При двух PATCH одной версии
выигрывает один; другой получает 412. Безусловное «последний записавший победил» не допускается.

PATCH пункта checklist использует ETag родительской WorkOrder. Возвращает WorkChecklistItem и новый ETag
заявки. Пункт и версия меняются одной транзакцией. false→true устанавливает checked_at серверным временем;
true→false обнуляет его; изменение только comment не переписывает checked_at.
POST-команды не требуют If-Match: конкуренцию защищают проверка состояния и транзакция; повтор — 409.
Если ответ создания потерян, перед повтором клиент выясняет наличие записи через список/карточку;
универсальный Idempotency-Key не входит в контракт.

## 5. Оборудование и неисправности

Инвентарный номер уникален, включая архив. Статусы оборудования: OPERATIONAL, UNDER_REPAIR, OUT_OF_SERVICE;
изменяются ENGINEER вручную и не закрывают неисправности автоматически. Архив запрещён при любом
незавершённом наряде, включая COMPLETED; CLOSED/CANCELLED не блокируют. Повторный archive — 409.
Restore снимает archived_at и ставит OUT_OF_SERVICE; повторный restore неархивного — 409.

Неисправность создаёт OPERATOR/ENGINEER; author_id всегда из сессии. OPEN → IN_PROGRESS при start связанного
ремонта → RESOLVED при close. До close выполненный ремонт оставляет Fault IN_PROGRESS. Отменить уже начатый
ремонт нельзя. Правка Fault — автором в роли OPERATOR либо ENGINEER, только OPEN без незавершённой заявки.
На Fault максимум один незавершённый REPAIR. RESOLVED нельзя использовать для нового ремонта; для повторной
поломки создают новую неисправность. REPAIR может быть и без Fault. Equipment/Fault/schedule должны совпадать.

## 6. Регламенты и индивидуальные графики

MaintenancePlan: scope=EQUIPMENT с equipment_id либо CATEGORY с category; строго одна область, изменить
её PATCH нельзя. interval_days=1..3650, first_due_on, checklist. План создаёт ENGINEER.
На **каждую пару plan_id+equipment_id за всё время один** MaintenanceSchedule (UNIQUE без active).
Текущие подходящие неархивные устройства подключаются атомарно при создании плана; новые устройства
подключаются к подходящим включённым планам. Для впервые подключённой пары:
`last_completed_on=null; next_due_on=max(first_due_on, local_today)`.

active = план включён AND оборудование не архивировано AND соответствует области плана.
Пауза плана, архив или уход из категории деактивируют график без удаления. Возврат/включение восстанавливает
тот же id и даты, даже если они просрочены. Если при выключенном плане добавили новое подходящее оборудование,
включение плана создаёт отсутствующую пару по правилу первого подключения. При наличии незавершённого
PLANNED смена категории запрещена. Выключенный план запрещает новые наряды/напоминания, но не мешает
закончить существующий наряд; close обновляет сохранённые даты и при active=false.

is_overdue = active AND next_due_on < local_today AND нет COMPLETED текущего срока.
В сам день ТО is_overdue=false. has_current_work_order учитывает CREATED/ASSIGNED/IN_PROGRESS/COMPLETED
на текущий срок, исключая CLOSED/CANCELLED.

При смене интервала нельзя иметь незавершённый PLANNED этого плана. Для всех графиков, включая неактивные:
если last_completed_on=null, next_due_on сохраняется; иначе next_due_on=last_completed_on+новый интервал.
Новый срок должен быть **строго позже последнего CLOSED planned_due_on** этого графика, иначе 409
NON_ADVANCING_DUE_DATE и полный откат плана/всех графиков/версии. Просрочка сама по себе не переносит дату.
Чек-лист плана заменяется целиком; существующие snapshot нарядов не меняются.

## 7. Заявки, завершение и отмена

REPAIR: fault_id необязателен, schedule_id запрещён. PLANNED: schedule_id обязателен, fault_id запрещён;
создаёт только ENGINEER. planned_due_on сервер копирует из графика под блокировкой. Автор из сессии.
Создание и назначение заранее разрешены. Максимум один незавершённый PLANNED на график; пара
(schedule_id,planned_due_on) не имеет двух **неотменённых** нарядов, включая CLOSED.

| Команда | Роль и исходное состояние | Результат |
|---|---|---|
| assign | ENGINEER, CREATED; ACTIVE TECHNICIAN | ASSIGNED |
| reassign | ENGINEER, ASSIGNED/IN_PROGRESS; другой ACTIVE TECHNICIAN | Статус сохраняется, REASSIGNED |
| start | Назначенный ACTIVE TECHNICIAN, ASSIGNED | IN_PROGRESS |
| checklist | Назначенный TECHNICIAN, IN_PROGRESS, PLANNED | Отметка snapshot, CHECKLIST_ITEM_UPDATED |
| complete | Назначенный TECHNICIAN, IN_PROGRESS; result, обязательные отметки | COMPLETED |
| close | ENGINEER, COMPLETED | CLOSED, одна WorkHistory и событие |
| cancel | ENGINEER, CREATED/ASSIGNED; непустой reason | CANCELLED, событие, без WorkHistory |

COMPLETE PLANNED разрешён только если `local_date(completed_at)+interval_days > planned_due_on`.
completed_at назначает сервер; иначе 409 TOO_EARLY_TO_COMPLETE и никаких изменений.
Пример: срок 05.11.2026, интервал 30 дней: 06.10 запрещено, 07.10 допустимо и даёт следующий срок 06.11.
Для interval_days=1 выполнить можно только в день срока или позже. Отдельные идентификаторы циклов не нужны.

CLOSE одной транзакцией создаёт историю результата и заменённых деталей, событие CLOSED, завершает Fault
либо обновляет график: last_completed_on=local_date(completed_at), next_due_on=last_completed_on+interval_days.
Дата приёмки не подменяет дату выполнения. Сохраняются FK и immutable snapshot результата/чек-листа.

CANCELLED: cancelled_at/by/reason обязательны; assignee_id сохраняется для аудита. Fault остаётся OPEN,
график не меняется; слот освобождён, повторная заявка на тот же Fault/срок разрешена. Повторная отмена — 409.
CLOSED/CANCELLED терминальны: нет PATCH, повторных переходов или удаления. Возврат на доработку и отмена
IN_PROGRESS/COMPLETED вне MVP. Ошибку результата до приёмки решают вне API; её автоматическое исправление
не подразумевается этим контрактом. WorkOrderEvent append-only, WorkHistory создаётся только при CLOSED.

## 8. ARQ и внутрисистемные напоминания

Worker tick не реже одного раза в час; точный момент задаётся конфигурацией. Использует local_today.
Активный график без COMPLETED текущего срока: T−3..T−1 включительно — THREE_DAYS_BEFORE; с T до выполнения —
ON_DUE_DATE. После простоя создаётся только актуальный тип, без пачки пропущенных предварительных сообщений.
Ровно один получательский экземпляр по UNIQUE(schedule_id,planned_due_on,type,recipient_id), атомарный insert.

Получатели: все ACTIVE ENGINEER и текущий ACTIVE TECHNICIAN наряда ASSIGNED/IN_PROGRESS, если назначен.
Позднее назначение/reassign уведомляет нового получателя на следующем tick в актуальном окне. Параллельные
tick не дублируют запись. Два станка одного CATEGORY-плана получают отдельные уведомления каждому инженеру.
Пример: два станка, два инженера, один назначенный техник на первом станке → пять записей одного актуального
типа: четыре ENGINEER и одна TECHNICIAN. На T−4 — ноль, на T−1 после пропуска — тот же набор предварительных,
на T — пять ON_DUE_DATE. Старые предварительные остаются историей, а не вновь создаются на T.

CANCELLED не меняет график и не создаёт новый цикл/дубли. COMPLETED прекращает генерацию ещё до close.
Пауза, архив, BLOCKED получатель не получают новых записей. Старые записи не удаляются: доступ к ним только
у своего получателя при текущей ENGINEER/TECHNICIAN роли; уведомление может описывать уже изменившееся
назначение/дату. Изменение даты не переписывает прежние уведомления. Прочтение не отслеживается.

## 9. Списки, поиск и сортировка

{items,total,limit,offset}; limit=1..100, default 20; offset>=0. Пустой результат/offset>=total — 200 items=[].
Диапазоны дат включительны, фильтры AND; date_from>date_to и аналоги — 422 INVALID_DATE_RANGE.
Для completed_from/to сравнивают local_date(completed_at). Пагинация не гарантирует snapshot между запросами
при параллельном создании/редактировании, но порядок при неизменных данных детерминирован.

Equipment q: name/inventory_number. Fault q: description. WorkOrder q: number/title/description.
Поиск подстроки без учёта регистра; % и _ — обычные символы, не SQL wildcard. q после trim непустой.
Equipment category/location — точное совпадение нормализованных строк; остальные фильтры по схемам.
WorkOrder sort=created_at,-created_at,status,-status; default -created_at. Для даты id в том же направлении;
для статуса порядок CREATED,ASSIGNED,IN_PROGRESS,COMPLETED,CLOSED,CANCELLED, затем created_at DESC,id DESC.
Другие списки: users login ASC,id ASC; equipment name ASC,id ASC; faults detected_on DESC,id DESC;
plans name ASC,id ASC; schedules next_due_on ASC,id ASC; events occurred_at ASC,id ASC;
history completed_at DESC,id DESC; notifications created_at DESC,id DESC. Если description операции задаёт
иной порядок, это дефект контракта, а не свобода реализации.

## 10. Транзакции и обязательные проверки

UNIQUE(lower(login)), UNIQUE(inventory_number), UNIQUE(plan_id,equipment_id), одна незавершённая REPAIR по
Fault, одна незавершённая PLANNED по графику, одна неотменённая PLANNED на schedule+due, одна WorkHistory
на WorkOrder, один Notification по получательскому ключу. Индексы, FK и/или общий порядок блокировок должны
обеспечивать эти инварианты при конкуренции; предварительная проверка в Python без защиты БД недостаточна.

Оборудование блокируется при archive/createWorkOrder/смене категории; график — при create PLANNED/close/
пересчёте интервала; WorkOrder — при любой команде/PATCH; активные администраторы — при смене роли/статуса.
Реализация выбирает совместимый общий порядок блокировок. Изменения статуса, события, Fault, графика и
истории — одна транзакция. При проигрыше гонки/сбое откат не оставляет ни события, ни частично обновлённой
связи. Ретраи внутри реализации не должны повторять бизнес-эффект. Внешних рассылок в MVP нет.
